# M3-done-rm: TDD Implementation Plan

Milestone: CLI `done` and `rm` commands for todo-cli
Date: 2026-05-29
Scope: `todo done <id>` and `todo rm <id>` CLI subcommands with error handling and edge cases

## Overview

M3 adds the final two CLI commands to complete the spec: `todo done <id>` flips a
todo's status from open to done, and `todo rm <id>` permanently removes a todo.
Both error with exit 1 on unknown IDs.

The storage layer already provides `TodoStore.done()` and `TodoStore.remove()` (from
M1-storage), and the CLI scaffolding from M2-cli provides the parser, main(), and
error-handling patterns. M3 wires these together and adds comprehensive CLI-level tests.

**Implementation status:** During M2-cli, `done` and `remove`/`rm` subcommands were
implemented ahead of schedule in both the parser and main() handler. Existing tests
cover the primary happy and error paths. M3 verifies and hardens the done/rm paths
with parser-level unit tests and edge-case coverage (field preservation, cross-command
interactions, idempotency, lifecycle workflow, error message format consistency).

## Prerequisites

- M1-storage complete: `TodoStore.done(id)` raises `KeyError` on unknown ID;
  `TodoStore.remove(id)` raises `KeyError` on unknown ID
- M2-cli complete: `_build_parser()`, `main()`, `_format_todo()`, `--store` flag,
  error-handling try/except patterns, `tests/conftest.py` fixtures

## Interface contract (from M1-storage)

```python
class TodoStore:
    def done(self, todo_id: int) -> None: ...       # raises KeyError if not found
    def remove(self, todo_id: int) -> None: ...     # raises KeyError if not found
```

## CLI command mapping (M3 scope)

| Spec command    | argparse subcommand  | TodoStore method       | Exit code (ok) | Exit code (err) |
|-----------------|----------------------|------------------------|----------------|-----------------|
| `todo done <id>`| `done` (pos: id int) | `store.done(id)`       | 0              | 1 (unknown id)  |
| `todo rm <id>`  | `remove` / alias `rm`| `store.remove(id)`     | 0              | 1 (unknown id)  |

## Design decisions

| Decision | Rationale |
|----------|-----------|
| `done` produces no stdout | Only `add` (echo) and `list` (display) produce output; state-change commands are silent |
| `rm` is an alias, not a separate command | argparse `aliases=["rm"]` — one implementation, two names |
| `args.command in ("remove", "rm")` check | argparse stores the actual subcommand string used (canonical or alias) in the subparsers dest; must check both |
| `KeyError` → exit 1 with stderr message | Spec: "Errors with exit 1 if id is unknown" |
| Parser uses `type=int` for id | Argparse validates input type; non-integer IDs fail at parse time with argparse error |

## Risks and mitigations

| Risk | Mitigation |
|------|-----------|
| `args.command` is "rm" vs "remove" when alias used | Check `args.command in ("remove", "rm")` to handle both |
| Done on already-done todo | Storage layer is idempotent (sets status="done" regardless); no special handling needed |
| Remove after done | Storage layer removes by ID regardless of status; no special handling needed |
| Error message format inconsistency | All error paths use same pattern: `error: no todo with id {id}` |
| Corrupted store on done/rm | Outer try/except for `(OSError, ValueError)` catches JSON parse errors |

## Scope boundaries

**In scope (M3-done-rm):**
- `done` subcommand: parser entry, handler, error path
- `remove` subcommand with `rm` alias: parser entry, handler, error path
- Edge cases: idempotent done, remove done todos, remove preserves others
- Corrupted-store error handling for done/rm paths
- Parser-level unit tests for done/remove/rm

**Out of scope:**
- Storage layer changes (done/remove already implemented in M1)
- CLI scaffolding changes (main(), _format_todo, --store already in M2)
- Interactive mode, tags, priorities, due dates
